# HiSilicon Kirin 970（Venice）BootROM

> 对象：华为 Nova 4（`VCE-AL00`）的 Kirin 970 BootROM。
> dump：`sources/venice/brom.bin`（64 KB）
> 说明：本文只保留**能从 dump 复现**的事实；原始逆向笔记属于私有项目，未随本仓库发布。

|---|---|

## 硬件档案（来自反汇编）

```
ROM[0x0] = 0x0004DBFC   初始 SP
ROM[0x4] = 0x00000049   复位向量（Thumb @0x48）
ROM[0x8..] = 0x000000B1 默认异常处理（→ 0xB0 的 b 0xB0 死循环）
ROM 大小 = 0x10000（64 KB）
```

### 内存

| 区域 | 地址 | 说明 |
|---|---|---|
| ROM | `0x0–0xFFFF` | BootROM 本体 |
| SRAM | `0x10000–0x7FFFF` | 栈顶 `0x4DBFC`；镜像装载区 `0x22000`；状态字 `0x21E04` |

### MMIO（`movw/movt` 扫描 + 上下文实测）

| 地址 | 推测用途 | 备注 |
|---|---|---|
| `0x4020A3A0` | **启动源**（bit15：0=flash / 1=USB） | xloader 也读同一位 |
| `0x4020A008` | 另一位 bit15 | 与上者关系未核实 |
| `0x4020A000` | 状态（`&0x78`） | `0x10`/`0x20` 表示不同阶段 |
| `0x4020A10C` | 就绪位（bit0） | |
| `0x40201E04` | 状态字镜像 | 与 SRAM `0x21E04` 同值 |
| `0x4023E004` | **时基**（`0x3c50` 用它算经过时间） | 必须单调 |
| `0x4023E000` / `0x4023E008` | 触发 / 命令掩码 | 写 `0xFFFFFFFF`、`0xC2` |
| `0x402050A8` / `0x40235114` | 时钟/PLL | |
| `0xBF100000` / `0xBF10C000` | **USB 设备控制器**（上下文 `0x20000` 存它的基址与端点指针） | |
| `0xBC182000`–`0xBC1831xx` | 另一块（USB PHY / 时钟，待定） | 约 30 个寄存器被访问 |
| `0xBDF0F000` | **SEB**（安全引擎） | 见下 |

### SEB 寄存器（实测有效位）

| 偏移 | 含义 | 仿真值 |
|---|---|---|
| `+0xAB4` | 命令完成（bit0） | 1 |
| `+0xABC` | 就绪（bit0） | 1 |
| `+0xAA4` | 命令字（写） | — |
| `+0xAAC` | 命令结果（读） | 0 = 成功 |
| `+0xAD4` | 安全类型 | **0 或 7** 走免验分支；真机 = 5（SECURE） |
| `+0x928` | 版本/身份（高字节须 `0xBF`） | `0xBF000000` |
| `+0xA00` | 哈希/签名完成（非 0 且 bit2=1） | 0x4 |
| `+0xBA0` | 结果码（1 = 成功） | 1 |
| `+0xE9C` | 密码引擎就绪（bit3） | 8 |
| `+0xFE9C` | 同上（另一入口） | 8 |
| `+0xA24` | 外设 ID 魔数 | `0xD5C63000` |

## 和 MTK 的差异

| 项 | MTK MT6853 | Kirin 970 |
|---|---|---|
| 指令集 | ARM | **Thumb**（profile 覆盖 `init_cpu` 钩子置 CPSR.T） |
| 初始 SP | 从 RAM 读 | **ROM[0]** 直接给 |
| 传输 | CDC-ACM（UART 模型） | **USB 控制器**（`0xBF10C000`） |
| 启动源 | `0x1000A000 & 0xF` | `0x4020A3A0` bit15 |
| 命令层 | `sub_F830` 循环 | VCOM `0xFE/0xDA/0xED/0xCD`（见私有项目文档） |

## 推进记录（每步都是"补一个寄存器/事件"后前进）

| # | 卡点 | 处理 |
|---|---|---|
| ① | `0x4020A000 & 0x78` 延时分支 | 给 `0x10` / `0x20`（不同阶段要求不同） |
| ② | `0x4023E004` 轮询"值变化" | 返回递增计数器（它是时基，单调即合理） |
| ③ | `0x4020A10C` bit0 | 置 1 |
| ④ | `0x2494` 等完成 | **`[ctx+0xe34]+4 != 0`** 才是"响应就绪"（不是事件计数） |
| ⑤ | `0x4A8` 比对返回值 | 注入 **`0x22000`**（它把返回值与参数比较） |
| ⑥ | SEB 就绪/命令 | 见上表四个寄存器 |
| ⑦ | 容器链解析 | 合成镜像：块1 type=1、块2 type=2 |
| ⑧ | 验签分发 `0x450` | 安全类型 0/7 → 免验分支，返回 0 |
| ⑨ | 跳转 | ELF `e_entry` 修正为 `0x23035`（= `0x22000+0x1000+0x35`） |

### 安全类型行为矩阵（`VENICE_TYPE`）

| 类型 | 结果 | 最后到达 |
|---|---|---|
| 0 / 1 / 3 | ✅ 跳转并执行合成镜像 | `0x726` |
| 5（真机 SECURE） | ❌ 卡在 `0x420` 的 SEB 查询 | `0x4F58` |
| 6 | ❌ 策略分发后停住 | `0x40E0` |
| 7 | ❌ **走到分段验签**，返回 `0xB0000001` | `0x3F40` |

### 策略分发表（`0x40E0` 的 tbb @ `0x4122`，实测字节 `28 28 24 18 24 04 24 04`）

| 类型 | 去向 | 行为 |
|---|---|---|
| 0 / 1 | `0x4172` | 再查 SEB bit `0x800000` |
| 2 / 4 / 6 | `0x416A` | 错误 `0xF100001B` |
| 3 | `0x4152` | 把类型写进 SEB 配置寄存器 |
| **5 / 7** | `0x412A` → `0x3F40` | **完整分段验签** |

`0x412A` 的第一个参数是 `movw r0,#0x3DC1` —— 这是 **Thumb 函数指针**（`0x3DC0` 是 memcpy 类函数），
不是数据地址。所以 `0x3F40` 形如 `verify(读回调, 块地址表, 长度, 缓冲)`：
`0x3E68` 存下的三段其实是**三个块的地址**（`0x22000` / `0x222CC` / `0x22598`），逐块校验块头。

### 验签内部结构（`0x3F40` 及其子函数）

```
0x3F40(verify_cb=0x3DC1, pairs, limit=0x4DC00, buf=0x400)
  ├─ 0x4240(局部结构) → 返回 0
  ├─ 每段：0x4260(cb, &ctx, block_addr, …)
  │    ├─ 0x44EC(cb, …)     经回调读块头（验证 magic/版本/type）
  │    ├─ 0x467C(…)
  │    └─ 0x43CC(cb, …)     遍历段，逐段 0x4A88
  │         └─ 0x4A88      读段描述符 [r6+8]；为 0 直接成功返回，否则算哈希/调 SEB
```

**回调 `0x3DC0` 是 memcpy 包装**：`if (src==dst) return 0; else memcpy(dst,src,len)`。

**失败链已定位到函数级**（探针逐级回读返回值）：

```
0x450 → 0x40E0(type5/7) → 0x3F40(cb=0x3DC1, pairs, 0x4DC00, 0x400)
   → 0x4260(cb, ctx, block=0x22000)
      → 0x44EC  读块头（0x22080，魔数正确）→ 0 ✓
      → 0x467C  (SEB base, 0x4DC00, …)
         → 0x4594 ………………… 0 ✓
         → 0x4C80 ………………… **0xB0000001** ✗
            → 0x4908 → 0x53A0
```

`0x53A0` 的入口条件：

```asm
0x53ae  cbz  r2, 0x5402      ; 输出指针为空 ⇒ 0xB0000001
0x53b0  cmp  r1, #1
0x53b2  beq  0x540e
0x53b4  cmp  r1, #2
0x53b6  bne  0x5402          ; 类型不是 1/2 ⇒ 0xB0000001
```

⇒ 根因是**块内 `+0x1A4` 必须是 1 或 2**（`0x4594` 把它写成指针，`0x53A0` 校验其值）。
合成镜像加上这个字段后，与真实镜像**到达同一位置**。
这个结构由 `0x4594` 填写，是下一步要反汇编的函数。

**type=7 的失败点值得深挖**：`0x450` → `0x40E0` → `0x3F40`（分段验签）→ 返回 `0xB0000001`（`0x5538` 的"参数为空"）。
推测原因：合成容器的段表字段（`+0x88` 高 16 位 = 段数、低 16 位 = 表偏移）没填对，
解析出全 0 的 (addr,len)，导致验签拿到空参数。
这也是构造畸形容器用例的入口。

## 熔丝位选择机制（与 MTK 同构）

`0x5028` 的算法（实测反汇编）：

```asm
循环 0x5538(base, 0x10..0x17, &word)   ; 读熔丝字
     popcount(word)                     ; SWAR 位计数
     r8 += 32 - popcount(word)          ; 累计"已烧写位"数
0x5538(base, 0x0B, &w)                 ; 读期望值
r2 = w & 0xff ; r3 = (w>>8) & 0xff
if r3 == 0xFF: r3 = r2 else r3 += r2
cmp r3, r8 → 相等才放行（否则 0xB0000008）
```

**为什么读熔丝后取反**：

| 原因 | 说明 |
|---|---|
| 未编程态是"全 1" | 烧写把 1 变 0 ⇒ `32-popcount` 就是"已烧写位数" |
| 空片天然得 0 | 未烧写的芯片自动落到默认槽，不会随机命中某把密钥 |
| 熔丝按位计价 | 用"位数"代替"位模式"，追加烧写不会让老校验失效 |
| 低熵选择器 | 位数当摘要，用来选密钥槽 / 校验产线烧写完整性 |

**可仿真的设备状态**（两边都由 SEB 返回，所以能软件化）：

| 状态 | 熔丝字 | 期望值（cmd 0x0B） |
|---|---|---|
| 未烧写（空片） | `0xFFFFFFFF` | `0` |
| 烧了 N 位 | 任意使 Σ(32−popcount)=N | `N` |
| 零售机 | 需真机读数 | 需真机读数 |

⚠️ 设计弱点：只比**位数**、不比**模式** ⇒ 密钥槽选择的熵 = 熔丝位数，而不是熔丝总位数。

## 现在能跑通的链路

```
复位 0x48 → PLL/时钟 → 控制器初始化（0x221C）→ 等完成（0x2494）
      → 装载区 0x22000 有数据 → 容器链解析（块1 type=1 / 块2 type=2）
      → 0x450 验签分发（类型 0/7 放行）→ 跳转 ELF e_entry
      → 执行合成桩（打印 + bx lr）→ 返回 BootROM 0x6E
```

关键开关：

| 开关 | 位置 | 说明 |
|---|---|---|
| 装载数据 | `venice._image()` | 把 `sources/venice/xloader_synth.bin` 写进 `0x22000` |
| 控制器完成 | `[ctx+0xe34]+4 = 0x22000` | 让 `0x2494` 认为"响应就绪" |
| 安全类型 | `0xBDF0FAD4` | 0/7 → 免验；5（真机 SECURE）→ 走完整验签 |
| 返回码 | `0x4A8` 期望 `0x22000` | 主线 `0x6AC`/`0x6BE` 会重试直到匹配 |

## BootROM ctx = SRAM `0x20000`（已定）

静态分析里长期悬着的 "ctx 绝对地址" 已确认就是 **`0x20000`**：

```
0x62e   str r3,[r2]        ; r2 = 0x20000 → 清零上下文
0x221C  建上下文（写 [+0]=0xBF100000、[+0xE34]=调用者结构…）
0x2494(r0=ctx) → 0x25A4 → 0x343C → 0x29F8(ctx)  初始化 VCOM 通道
0x2D0C  movw r3,#0x350D ; [ctx+0xC0] = 0x350D（帧处理函数）
0x2D10  r2 = ctx+0x3D8 ; [ctx+0xBC] = 帧缓冲
```

| 偏移 | 绝对地址 | 含义 |
|---|---|---|
| +0x3D8 | `0x203D8` | 帧缓冲 |
| +0xB8 | `0x200B8` | 帧长度 |
| +0xBC | `0x200BC` | 缓冲指针 |
| +0xC0 | `0x200C0` | 处理函数（`0x350D`） |
| +0xE34 | `0x20E34` | 调用者结构指针 |

## 控制器上下文（SRAM `0x20000`）

里面有 UTF-16 字符串 `"HISILICON USB SER"` ⇒ 这是 USB 设备控制器的上下文。

| 偏移 | 值 | 含义 |
|---|---|---|
| +0x00 | `0xBF100000` | 控制器基址 |
| +0x04 | `0x00020E38` | 缓冲区尾 |
| +0x08 | `"HISILICON USB SER"` | 序列号字符串描述符 |
| +0x28 / +0x2C | `0x12` / `0x0E` | 长度/索引 |
| +0x30 | `0x00020000` | 自引用 |
| +0x64 / +0x68 | `0xBF10C800` / `0xBF10C810` | 端点寄存器指针 |
| +0x9C | `0xBF10C820` | 端点寄存器指针 |
| +0xE34 | 调用者结构指针 | `+4` 就是"响应就绪"标志 |

## 事件队列（`0x2494`）

退出条件是 `[ctx+0xe34]+4 != 0`（`0x2570`–`0x257a`），不是事件计数。
队列本身：`[ctx+0xe30]` = 消费者指针，环形区 `ctx+0xa30`–`ctx+0xe30`，每项 4 字节；
待处理计数在 `0xBF10C40C`。

**事件字格式**（`0x25a4` 反汇编）：

| 位 | 含义 |
|---|---|
| bit0 | 方向（0=读 / 1=写） |
| bits1-4 | 槽位/队列号 |
| bits6-9 | UPIU 响应类（`0x40` / `0xc0`） |
| bits8-11 | 事件类型（1/2，见 `0x2608`） |

**底层驱动轮询模式**（`0x19c4`–`0x1a68`）：先写命令字 `[rX+0xc]`（`0x401`/`0x402`/`0x408`），
再轮询同一寄存器 —— **bit10=1 表示忙**，最多 `0x3E8` 次。

## 还缺什么

1. **SECURE（type=5）路径**：完整验签走不到底（当前靠免验分支）
2. **真正的传输/存储模型**：现在是"直接注入数据"，没有 DMA 与 UPIU 响应
3. **VCOM 协议层**：`emu/transport.py` 仍是 MTK 的 CDC-ACM 分片
4. **eFuse / 芯片 ID**：`0x800C5555` 之类魔数的来源
