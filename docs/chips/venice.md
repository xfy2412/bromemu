# HiSilicon Kirin 970（Venice）BootROM

> 对象：华为 Nova 4（`VCE-AL00`）的 Kirin 970 BootROM。
> dump：`sources/venice/brom.bin`（64 KB）

## 状态

| 项 | 状态 |
|---|---|
| 从复位向量启动 | ✅ |
| 跑过 500 万条指令（不崩） | ✅ |
| **进入 flash 启动路径** | ✅ 已到存储控制器读 boot data 阶段（`0x221c` → `0x2494`） |
| 读出 xloader / 继续到校验 | ⏸ 卡在控制器事件队列：`0x2494` 等 `0xBF10C40C` 的完成事件 |
| 到达 USB 下载态 / 命令循环 | ⏸ 未到（需要建模 MMIO：SEB / eFuse / USB） |
| VCOM 帧收发 | ⏸ 未接（传输层仍是 MTK CDC-ACM 模型） |

## 硬件档案（来自反汇编）

```
ROM[0x0] = 0x0004DBFC   初始 SP
ROM[0x4] = 0x00000049   复位向量（Thumb @0x48）
ROM[0x8..] = 0x000000B1 默认异常处理（→ 0xB0 的 b 0xB0 死循环）
ROM 大小 = 0x10000（64 KB）
```

### 内存

| 区域 | 地址 | 说明 |
|---|---|---|
| ROM | `0x0–0xFFFF` | BootROM 本体 |
| SRAM | `0x10000–0x7FFFF` | 栈顶 `0x4DBFC`；镜像装载区 `0x22000`；状态字 `0x21E04` |

### MMIO（`movw/movt` 扫描结果）

| 地址 | 推测用途 | 备注 |
|---|---|---|
| `0x4020A3A0` | **启动源**（bit15：0=flash / 1=USB） | xloader 也读同一位 |
| `0x4020A008` | 另一位 bit15 | 与上者关系未核实 |
| `0x40201E04` | 状态字镜像 | 与 SRAM `0x21E04` 同值 |
| `0x402050A8` / `0x40235114` | 时钟/PLL | |
| `0x40235410` / `0x40235E24` | 时钟/复位 | |
| `0xBF100000` / `0xBF10C000` | **USB 设备控制器**（上下文 `0x20000` 里存的就是它的基址与端点指针） | 传输层的真正入口 |
| `0xBC182000`–`0xBC1831xx` | 另一块（USB PHY / 时钟一类，待定） | 约 30 个寄存器被访问 |
| `0xBDF0E004` / `0xBDF03DC1` | **SEB** | base `0xBDF0F000` |
| `0x800C5555` / `0xF600082B` | 未知 | 可能是魔数而非地址 |

## 和 MTK 的差异（对本项目的影响）

| 项 | MTK MT6853 | Kirin 970 |
|---|---|---|
| 指令集 | ARM | **Thumb**（profile 覆盖 `init_cpu` 钩子置 CPSR.T） |
| 初始 SP | 从 RAM 读 | **ROM[0]** 直接给 |
| 传输 | CDC-ACM（UART 模型） | **USB 控制器**（`0xBC18xxxx`） |
| 启动源 | `0x1000A000 & 0xF` | `0x4020A3A0` bit15 |
| 命令层 | `sub_F830` 循环 | VCOM `0xFE/0xDA/0xED/0xCD`（见 BootROM 流程文档） |


## 当前卡点：USB 控制器初始化

推进记录（每步都是"补一个寄存器/事件"后前进）：

| 阶段 | 卡点 | 处理 |
|---|---|---|
| ① 延时/轮询 | `0x4020A000 & 0x78` | 给 `0x10`/`0x20`（不同阶段要求不同） |
| ② 等待响应 | `0x4023E004` 值变化 | `read_mmio` 返回递增计数器 |
| ③ 等就绪位 | `0x4020A10C` bit0 | 置 1 |
| ④ USB 控制器等待 | `0x2494` 等 `[ctx+0xe34]+4`（"响应就绪"） | ✅ 注入该字段后不再自旋 |
| ⑤ 初始化返回值 | `0x4a8` 要求 `0x2328` 返回 `0x22000` | ✅ 注入该值后通过 |
| ⑥ SEB 就绪/命令 | `0x4FABC` / `0x4FAB4` 轮询、`0x4AA4` 写命令 | ✅ 建模后通过 |
| ⑦ 容器链解析 | 块1 type=1、块2 type=2 | ✅ **通过**（合成镜像 `xloader_synth.bin`） |
| ⑧ 验签分发 `0x450` | 安全类型 | ✅ 类型 0/7 时返回 0（"免验"分支） |
| ⑨ **跳转** | ELF `e_entry` | ✅ **BootROM 跳进合成镜像并执行了桩代码**（返回后落到 `0x6E` 死循环） |


控制器寄存器（反汇编观测；`0x20000` 处的上下文里有 UTF-16 字符串 **"HISILICON USB SER"** ⇒ 这是 **USB 设备控制器**，不是存储）：

| 地址 | 行为 |
|---|---|
| `0xBF10C000` | 基址（写进上下文 SRAM `0x20000` 的 `+0`） |
| `0xBF10C100` | 上下文记录到 `ctx+0xa2c`；`+0x30c` 即事件计数寄存器 |
| `0xBF10C400` | 写入 `0xFFF81C70` 形态的地址（DMA 描述符指针） |
| `0xBF10C404` / `0xBF10C408` | 写 `0` / `0x400`、`0x80000000`（命令与标志） |
| `0xBF10C700` / `0xBF10C704` / `0xBF10C720` | 写 `1`、`0x200000`、`3`（门铃/命令） |
| `0xBF10C800` / `0xBF10C804` / `0xBF10C808` | 写 `0x500`、`0x1`（传输设置） |
| `0xBF200000`–`0xBF2002xx` | 另一块（PHY/时钟类） |

上下文（SRAM `0x20000`）关键字段：

| 偏移 | 值 | 含义 |
|---|---|---|
| +0x00 | `0xBF100000` | 控制器基址 |
| +0x04 | `0x00020E38` | 缓冲区尾 |
| +0x08 | `"HISILICON USB SER"` (UTF-16) | 序列号字符串描述符 |
| +0x28 / +0x2C | `0x12` / `0x0E` | 长度/索引 |
| +0x30 | `0x00020000` | 自引用 |
| +0x64 / +0x68 | `0xBF10C800` / `0xBF10C810` | 端点寄存器指针 |
| +0x9C | `0xBF10C820` | 端点寄存器指针 |

事件处理链：`0x2494`（收事件）→ 事件字 `bit0/bit1..5` 分类 → `0x25a4` / `0x2608`（各事件处理）→
`0x252a` 里看 `ctx+0xe34`（`+4`/`+0xc`/`+0x10`）判断是否超时（`0x3c50`，上限 `0x493e0`，
超时返回 `-3` ⇒ 触发 `0x2328` 重试）。

**事件字格式**（`0x25a4` 反汇编）：

| 位 | 含义 | 代码 |
|---|---|---|
| bit0 | 方向（0=读 / 1=写） | `ands r7, r1, #1` |
| bits1-4 | 槽位/队列号 | `ubfx r4, r1, #1, #4` |
| bits6-9 | UPIU 响应类（`0x40` / `0xc0`） | `and r2, r5, #0x3c0` |
| bits8-11 | 事件类型（1/2，见 `0x2608`） | `ubfx r1, r1, #8, #4` |

**队列结构**：`[ctx+0xe30]` = 消费者指针，环形区 `ctx+0xa30`–`ctx+0xe30`，每项 4 字节；
控制器把"待处理计数"放在 `0xBF10C40C`（= `[ctx+0xa2c] + 0x30c`）。

**底层驱动轮询模式**（`0x19c4`–`0x1a68`）：先写命令字 `[rX+0xc]`（`0x401`/`0x402`/`0x408`），
再轮询同一寄存器 —— **bit10=1 表示忙**，最多 `0x3E8` 次，退出后把该寄存器当状态返回。

**注入实验（2026-11-25）**：

1. 一开始"只注入一次"失败 —— 因为 `0x221c` 的清零循环（`0x2254`，清 `0x20000`–`0x20E38`）
   会把事件覆盖掉
2. 改成"每次读 `0xBF10C40C` 时若队列头为 0 就补事件"，事件**确实被处理了**
   （`0x2524` 命中由 0 变 4），但命令仍然超时重试
3. 处理链：`0x25a4` → `0x343c`（按 `[ctx+0xa]` 分派：0 → `0x29f8`，非 0 → `0x3300`）

⇒ 还缺"命令完成"的实质内容：`0x343c` 之后要能读到 UPIU 响应/传输状态，
这是下一步要建模的部分（响应结构在 DMA 缓冲里，零值被当成失败）。

**下一步**：读懂 `0x25a4` / `0x2608` 的事件字格式，然后在 `write_mmio` 里拦门铃写、
把合成事件塞进 `[ctx+0xe30]` 指向的队列，并让 DMA 把"假 xloader"搬进描述符缓冲。
## 已经跑通的（2026-11-25）

```
复位 0x48 → PLL/时钟 → USB 控制器初始化（0x221C）→ 等待完成（0x2494）
      → 装载区 0x22000 有数据 → 容器链解析（块1 type=1 / 块2 type=2）
      → 0x450 验签分发（类型 0/7 直接放行）→ 跳转 ELF e_entry
      → 执行合成桩（bx lr）→ 返回 BootROM 0x6E
```

关键开关：

| 开关 | 位置 | 说明 |
|---|---|---|
| 装载数据 | `venice._image()` | 读 `sources/venice/xloader_synth.bin` 写进 `0x22000` |
| 控制器完成 | `[ctx+0xe34]+4 = 0x22000` | 让 `0x2494` 认为"响应就绪" |
| 安全类型 | `0xBDF0FAD4` | **0 或 7** 才走免验分支（真机是 5=SECURE） |

## 还缺什么

1. **SEB 建模**：`0xBDF0F000` 的 `+0xABC` 就绪位、`+0xAD4` 安全类型、`+0xAC0..+0xACC` 策略写
   —— 不建模会在校验路径死等
2. **USB 控制器建模**：`0xBC182000`/`0xBC183000` 两块，至少要能收发 512 B 包
3. **VCOM 传输层**：把 `emu/transport.py` 的 MTK 分片换成 HEAD/DATA/TAIL/INQUIRE + CRC16(0x1021)
   —— 帧格式在 `docs/protocol/vcom.md`（待补），实现进 `emu/transport.py`
4. **eFuse / 芯片 ID**：`0x800C5555` 之类魔数的来源
